# Daily Paper Conclusion Assistant

Start and re-enter through `l1-daily-paper-conclusion-core` before any diagnosis, tool, widget or final response. Root and byte-identical `skills/inflak-daily-paper-conclusion/SKILL.md` discovery alias represent the same entry, not separate routers. Paths below are plugin-relative.

## Layer Ownership and Four Pathways

- **Interaction Pathway:** user/return → L1 → L2 gap + exact registry selection → L3 semantic design → L4 render → L1.
- **Execution Pathway:** user/return → L1 → L2 plan → selected executor/current active `main_model` → L1. L2 directly realizes the instruction, without L3/L4 or separate executor skill.
- **Host Agent Return:** L1 → host through existing `bypass` or `direct_answer` when appropriate, not collection/synthesis disguised as host response.
- **Completion:** only L1 owns canonical state, merge authority and `decision: "end"`. Every L2/L3/L4/executor result, partial failure, failure, dismissal or cancellation immediately returns to this plugin's L1 before another action.

L2 `l2-daily-paper-conclusion-planner` binds H/T/I/Aug/A/G, assesses every registered gap as open/resolved/not applicable from current evidence, and chooses one by real dependencies. Applicable open input gaps prohibit final execution; bounded preparation leaves choices open and returns L1. Silence is not delegation; supplied scoped permission may settle a choice without a ritual widget. L3 designs only the exact selected interaction with full local eight-part handoff; invalid selection returns L1 without substitution. L4 `l4-daily-paper-conclusion-renderer` implements that profile, exact returns and local 266px host-UI/security rules, never task execution or merge.

## Paper Dependencies and Evidence

Authorized actual public arXiv source/date-range or paper limit/focus/output → real listing collection/filter/dedup → per-paper evidence card or explicit unavailable/skip record → supported theme map → current digest/revision → final acceptance. These are dependencies, not required widget visits. Partial/empty collection and weak inclusion/theme evidence require judgment only when materially unresolved; settled scope is not repeatedly approved.

Keep canonical arXiv IDs/URLs, real metadata/abstract access status, duplicates/skips, inclusion decisions, theme-to-paper support and coverage caveats. Missing browsing capability or inaccessible abstracts cannot become fabricated papers or conclusions. Scope/evidence/direction changes invalidate affected digest/acceptance/export while preserving history and unrelated successes.

## Registries and Domain Interactions

Use `registry/planners.json`, `registry/widgets.json`, `registry/tools.json` for stable IDs/canonical paths/eligibility/fixed returns. Five interactions remain under `daily-paper-conclusion-`: scope-setup, candidate-collection-review, paper-inspection-resolution, synthesis-direction-review, digest-acceptance-review. L1 owns typed lifecycle and lossless return mapping. main_model means active session, not a host tool; render_html_widget is L4-only. No new host API or undocumented renderer argument is implied.

## Final Presentation and Acceptance

Show the actual top conclusion and a clearly labeled **1-2 sentence critical review** grounded in available paper evidence, then paper highlights, themes, source links and coverage caveats. Critical review identifies a supported limitation, assumption, evidence gap or implication and distinguishes inference and metadata/abstract-only boundaries; no invented criticism. Missing/unsupported critical review requires L2 repair, not renderer prose. Require exact-current acceptance with no material revision pending; copy/export alone is not acceptance. No confirmation checkbox or second approval gate; cancelled/unavailable outcomes are not success.
