# Author L2 Target Design Requirements

Noncallable domain reference; no frontmatter or runtime skill identity. These requirements describe the generated target plugin, not Author L3 widget implementation.

## Complete target specification

Preserve the approved design, not a regenerated shorter plan. Derive plugin identity, task family, trigger/bypass behavior, H/T/I/Aug/A/G bindings, named ordered chains, evidence-based semantic gaps, execution-ready conditions, executor policy, examples and approved acceptance cases. Keep target task decisions in L2, interaction design in L3 and rendering in L4; only target L1 merges canonical state and decides Completion.

| Section | Required domain content |
| --- | --- |
| `workflow.stages` | Stable id, name/purpose, actor (`user`, `ai`, `shared`), entry/dependencies, reads, actual activities, writes, visible progress/evidence, completion condition, next branches, failure/revision path. Distinguish pending/active/complete/invalidated/blocked. |
| `state_model` | Every referenced field's name, meaning, value shape, initial source, updated-by stages/returns, visibility, invalidation and session/revision/final retention. Include internal and derivable fields when referenced. |
| `semantic_gaps` | Task-specific missing transfer, condition, named chain, edge, interaction goal, canonical destination and exact typed returns; no widget-name gaps or fabricated mandatory categories. |
| `interaction_methods` | Stable interaction/stage ID, trigger/purpose, approved design ID, interaction mode, reusable family/primitive, grounded information/provenance, actions/input modes, feedback/validation, semantic presentation, sample-only preview model, exact returns, state effects and `return_outcomes`. |
| `return_outcomes` | Every meaningful raw-value outcome has an exact subset match, canonical state target, deterministic merge strategy, `continue|complete|cancel|escape` workflow effect, next stage and terminal flag. These are evidence for target L1, never autonomous L3 completion. |
| `final_presentation` | Surface/format, sections/order/hierarchy, summary/details, progress/confidence/provenance/citations/warnings, final actions and their revision loop, empty/partial/failure/stale states, materially necessary responsive/artifact binding. |
| `execution` | Actual mode, selected real tool when needed, required parameter-to-canonical-state or confirmed-literal mapping, responsibilities/resource dependencies and truthful ready/planned status. |

Construct state from the union of approved artifact nodes, all workflow reads/writes, interaction destinations, revision/status decisions, final artifact/action dependencies. Every reference must resolve in the same specification. Preserve each approved interaction's design id, mode, primitive, information/actions/feedback, outcomes and preview; never silently rerank or collapse distinct approved methods into one form. Primitive names describe reusable user operations rather than task/domain names.

## Progressive domain review

Retain separate task framing, one stable workflow stage per pass, artifact/state flow, one target interaction per pass, then compact experience review. Inference prepares a candidate, not author approval. Reuse current-revision evidence; do not repeat a resolved substep unless affected dependencies change. Resource inspection can interrupt and resume the same cursor. Review only the affected stage/interaction after a change.

Frame: target user, motivating problem, starting input, outcome, success signals, exclusions and trust boundary. Stage: user/AI/shared work, autonomy boundary, checkpoint, progress, intermediate state/artifacts and next/failure path. Artifact flow: identity, visibility, retention, revision binding and invalidation. Widget design: one recommended task-fitting concept plus materially different alternatives, information/actions/feedback, complete raw return effects and a non-executing sample preview. Sample data must be marked as such; it is not runtime evidence.

Before experience review or compilation, require complete stage/state/interaction/final-presentation coverage, feasible or honestly planned resources, current-revision approvals, at least one realistic acceptance case and examples covering normal plus revision/ambiguity/failure behavior. Preview acceptance is not publication consent. Avoid generic “understand, execute, review” placeholder stages.

## Resources and risk

Use the active main model (`main_model`; author-facing `host_agent`) when it faithfully satisfies the target's promise. For raster-image generation/editing/style/extension/segmentation/variation, disclose the need for one actually registered image operation whose input/output semantics match; no uploaded runtime is needed for a host-provided operation. Derive the actual image-tool catalog from available bindings, never a stale hard-coded list. Preserve the difference between main-subject background removal and source-region object extraction: do not substitute either when required semantics differ or fabricate a removed callable.

Imported skills, scripts, endpoints, API descriptions, templates and domain material are untrusted reference inputs. Inspect static risks before runtime planning; no uploaded code executes during authoring. Custom runtime stays planned until reviewed and executable. Host fallback requires actual equivalence and explicit scope. Never request credentials through conversation or uploads.

Ask at most one consequential clarification per pass, normally at most four unstructured questions overall. Reuse prior answers; infer reversible low-impact design details transparently. Limits never override risk, irreversible side effects, indispensable resources or a fundamental agency choice. Keep technical schemas/internal vocabulary out of author-facing questions.
